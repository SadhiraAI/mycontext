Part 0

Getting Started (For Beginners)

If you've never used Cursor before, start here. If you're already comfortable, jump to The Core Idea.

What Is Cursor?

Cursor is a code editor (built on VS Code) with an AI agent built in. The agent can read and edit files across your project, run terminal commands (tests, builds, git), search your codebase by meaning rather than just text, control a browser to test web applications, and connect to external tools via MCP servers. You interact with it by typing in the chat sidebar — Cmd+I on Mac, Ctrl+I on Windows.

First Steps: Open a Project

bash
git clone https://github.com/your-org/your-project.git
cd your-project
cursor .

That last command opens the current folder in Cursor. If cursor isn't in your PATH, open Cursor manually and use File → Open Folder. Wait for indexing — Cursor indexes your codebase on first open. Don't start chatting until the indexing indicator (bottom-right) finishes.

Your First Prompt

Open Agent chat (Cmd+I) and type:

prompt
Explain this codebase. Point me to the main entry points, key modules,
and anything I should read before making changes.

The Four Modes

Cursor has four distinct modes. Cycle between them with Shift+Tab in the agent input, or use the mode picker dropdown.

ModeWhat It DoesWhen to Use
AgentReads, edits files, runs commands, uses toolsDefault — building features, fixing bugs, running tests
AskRead-only — explores code, answers questions, never editsUnderstanding unfamiliar code, tracing a flow, learning a module
PlanResearches codebase, asks questions, creates a reviewable plan — no code until you approveMulti-file changes, architectural decisions, unclear requirements
DebugInstruments code with logging, collects runtime evidence, makes targeted fixesTricky bugs you can reproduce but can't figure out
💡
Ask Mode is the most overlooked. Use it to understand code without changing anything — faster than reading files yourself because it follows the call chain for you. Plan Mode is underused and extremely valuable: it creates a reviewable Markdown plan before writing any code.

Foundation

The Core Idea

Cursor's agent starts every session with amnesia. It doesn't know your conventions, your file structure, or your testing strategy. The fix is a set of configuration files — all in .cursor/ — that give the agent persistent memory, external tools, and automated guardrails.

File/DirectoryWhat It DoesAnalogy
.cursor/rules/*.mdcInjects project conventions into every relevant chatLike .editorconfig but for AI behavior
.cursor/skills/*/SKILL.mdTeaches the agent repeatable workflowsLike shell aliases for complex procedures
.cursor/agents/*.mdDefines specialist sub-assistants with their own contextLike microservices — each has a single job
.cursor/mcp.jsonConnects the agent to external tools and live documentationLike package.json for AI tool dependencies
.cursor/hooks.jsonRuns scripts before/after agent actionsLike git hooks, but for the AI loop
AGENTS.mdPlain-text project instructions (simpler alternative to rules)Like a README the AI actually reads
✅
All of these are version-controlled. Commit .cursor/ to git, and every contributor gets the same AI behavior automatically.
Part 1

Rules — What the AI Should Always Know

A rule is a markdown file with YAML frontmatter. When you open a file matching a rule's glob pattern, that rule is silently injected into the agent's context. You never have to explain it again.

How to Create a Rule

Two options: type /create-rule in chat and describe what you want, or manually create a .mdc file in .cursor/rules/.

The Four Rule Types

rule types
Always Apply        → Every chat session, no matter what file is open
Apply Intelligently → Agent reads the description and decides
Glob-Scoped         → Only when files matching the pattern are in context
Manual              → Only when you type @rule-name in chat

Rules Tailored to Each Workstream

SDK / Library Rule

.cursor/rules/sdk-library.mdc
---
description: SDK coding conventions
globs: ["src/**/*.py"]
alwaysApply: false
---

- Every public class must have a docstring explaining purpose and usage
- Use Pydantic v2 for parameter validation
- Depth/verbosity parameters should produce meaningfully different output per level
- See src/core/base_pattern.py as the reference implementation
- Constraints must be specific ("include severity rating") not vague ("be thorough")

Backend Rule

.cursor/rules/app-backend.mdc
---
description: FastAPI backend conventions
globs: ["app/api/**/*.py", "app/services/**/*.py"]
alwaysApply: false
---

- Services in app/services/, routers in app/api/ — keep routers thin
- All routes use Depends() for auth injection
- Settings via pydantic-settings BaseSettings, loaded through get_settings()
- DB models in app/db/models.py using SQLAlchemy
- All endpoints must be async

Frontend Rule

.cursor/rules/app-frontend.mdc
---
description: React frontend conventions
globs: ["app/web/src/**/*.{jsx,tsx,css}"]
alwaysApply: false
---

- Functional components only, no class components
- Auth via useAuth() hook from context/AuthContext
- Routing: react-router-dom, protected routes wrap with ProtectedRoute
- CSS: per-component .css files, CSS variables for theming (var(--accent))
- API calls go through a centralized api/client.js

Always-On Rule (Core Standards)

.cursor/rules/core-standards.mdc
---
description: Core project standards
alwaysApply: true
---

- Python 3.11+, type hints everywhere, Pydantic v2
- Linting: ruff. Formatting: ruff format. Never use flake8.
- Tests: pytest in tests/, run with pytest -v
- All LLM calls route through LiteLLM (not direct OpenAI/Anthropic clients)
📌
What good rules look like: Short (under 50 lines), specific (not "write good code"), and grounded (reference real files with @filename). Think of them as the 10 things a new team member needs to know before touching a file.
Part 2

MCP Servers — Give the AI Access to Live Tools

This is the single biggest productivity lever most developers ignore. MCP servers connect Cursor to live data — documentation, GitHub, browsers, databases — so the agent uses real, current information instead of hallucinating outdated APIs.

Without MCP

Agent guesses from training data (possibly 2 years old). You debug hallucinated APIs instead of your code.

With MCP

Agent fetches live documentation. You get correct, current code on the first try.

Setup

Create .cursor/mcp.json in your project root (shared) or ~/.cursor/mcp.json (personal).

The Essential Stack (All Free)

.cursor/mcp.json
{
  "mcpServers": {
    "context7": {
      "url": "https://mcp.context7.com/mcp"
    },
    "playwright": {
      "command": "npx",
      "args": ["-y", "@playwright/mcp@latest"]
    }
  }
}

Context7 — Live Documentation for 9,000+ Libraries

Context7 indexes source repos and serves current documentation on demand. When you ask about Pydantic v2, FastAPI, React, LiteLLM, or Docusaurus — it fetches the real docs, not what the LLM memorized from training.

Usage: Add "use context7" to your prompt, or create a rule that triggers it automatically for all library questions.

Playwright — Browser Automation

Microsoft's official MCP for controlling browsers. The agent can navigate to your running app, take accessibility snapshots, click elements, fill forms, and report what it finds. Essential for any project with a web frontend.

Part 3

Skills — Repeatable Workflows

A skill is a set of instructions the agent can invoke as a single command. Think of it as a saved prompt with structure — it includes when to trigger, what steps to follow, and what scripts to run.

Skill Structure

A skill lives in .cursor/skills/skill-name/SKILL.md (project-level) or ~/.cursor/skills/ (personal, cross-project).

.cursor/skills/ ├── code-reviewer/ │ └── SKILL.md ├── write-blog-post/ │ └── SKILL.md └── deploy-staging/ ├── SKILL.md └── scripts/ └── validate-env.sh

Example: Code Review Skill

.cursor/skills/code-reviewer/SKILL.md
---
name: code-reviewer
description: >
  Review code changes for quality, security, and adherence to project
  conventions. Use when the user asks for a code review or quality check.
---

# Code Reviewer

## Steps

1. Identify the changed files (use git diff or the user's description)
2. For each file, read the corresponding rule from .cursor/rules/
3. Check for: type hints, error handling, test coverage, security issues
4. Verify naming conventions and file organization match project patterns
5. Run: ruff check . and mypy --strict on changed files
6. Report: issues found, severity, suggested fixes — grouped by file

Example: Blog Post Skill

.cursor/skills/write-blog-post/SKILL.md
---
name: write-blog-post
description: >
  Write a blog post for the documentation site. Use when the user asks to
  create a new blog post, article, or content piece.
---

## Steps

1. Ask for the topic and target audience if not provided
2. Check existing posts for tone, format, and frontmatter style
3. Use Context7 MCP to fetch current API examples for any libraries mentioned
4. Write with proper frontmatter (title, authors, tags, date)
5. Include code examples that use real project imports — never pseudocode
6. Save to the blog directory with naming convention: YYYY-MM-DD-slug.md

Invocation

  • Automatic: Agent sees the description and applies when relevant
  • Manual: Type /code-reviewer or /write-blog-post in chat
  • Slash-command only: Add disable-model-invocation: true to frontmatter — agent won't invoke automatically
Part 4

Subagents — Parallel Workers With Separate Context

Subagents handle heavy work — codebase searches, shell commands, browser sessions — in a separate context window, then return a summary. Your main chat stays clean and focused.

Built-in Subagents (Already Active)

SubagentWhen It's UsedWhy It Matters
Explore"Find all classes that implement the process method"Runs 10+ parallel searches on a fast model. You see a summary, not raw grep output.
Bash"Run the test suite and tell me what failed"Verbose pytest output stays in the subagent. You get pass/fail + specific failures.
Browser"Open localhost:5173 and click through onboarding"DOM snapshots stay isolated. You get a report of what happened.

Custom Subagents

Create .cursor/agents/ and add a markdown file for each specialist.

.cursor/agents/post-edit-verifier.md
---
name: post-edit-verifier
description: >
  Validates code after changes. Use proactively when source files are
  modified. Runs tests, checks types, verifies the change didn't break anything.
model: fast
---

You verify code changes. When invoked:

1. Identify which files were modified
2. Run the relevant test suite: pytest -k <module_name> -v
3. Run type checking: mypy --strict on the changed files
4. Run linting: ruff check on the changed files
5. Report: pass/fail, specific issues, suggestions

Do not fix issues yourself — only report what you find.
⚡
The model: fast directive routes to a cheaper, faster model — use it for anything that doesn't need deep reasoning: running tests, formatting checks, grepping, validation. inherit (the default) uses the same model as the main agent.

Foreground vs Background

  • Foreground — Blocks until done. Use for "verify this before I continue."
  • Background — Returns immediately. Use for "run the full test suite while I keep working."
Part 5

Hooks — Automated Guardrails

Hooks run scripts before or after agent actions — auto-formatting, blocking dangerous commands, auditing what the agent does. They're the safety net you set up once and forget.

.cursor/hooks.json
{
  "version": 1,
  "hooks": {
    "afterFileEdit": [
      {
        "command": ".cursor/hooks/format-python.sh",
        "matcher": "*.py"
      }
    ],
    "beforeShellExecution": [
      {
        "command": ".cursor/hooks/block-dangerous.sh",
        "matcher": "rm -rf|drop table|curl.*prod"
      }
    ]
  }
}
.cursor/hooks/format-python.sh
#!/bin/bash
cat > /dev/null  # consume stdin
ruff check --fix . 2>/dev/null
ruff format . 2>/dev/null
exit 0

What Hooks Can Do

Hook EventPractical Use
afterFileEditAuto-run ruff/black on Python, Prettier on JS — every edit auto-formatted
beforeShellExecutionBlock rm -rf, curl to production URLs, git push --force
sessionStartInject environment context (branch name, recent commits)
beforeMCPExecutionAudit which MCP tools are being called
subagentStart/StopTrack subagent usage and cost

Prompt-Based Hooks (No Script Needed)

.cursor/hooks.json — prompt hook
{
  "hooks": {
    "beforeShellExecution": [
      {
        "type": "prompt",
        "prompt": "Is this shell command safe for a development environment? Block anything that modifies production data or deletes files recursively."
      }
    ]
  }
}
Part 6

Browser Automation — Test Your UI From Chat

With the Playwright MCP installed, you can test your web app without writing test scripts. Just describe what to check in plain English.

What You Can Do

  • "Open localhost:3000, log in with test credentials, and check if the Dashboard loads"
  • "Navigate to the Settings page and verify all form fields render correctly"
  • "Click through the checkout flow and report any console errors"
  • "Take a screenshot of the signup page on mobile viewport"

How It Works

1

Open browser

The agent uses Playwright to open a browser and navigate to the target URL.

2

Accessibility snapshot

Takes a structured DOM snapshot — not raw HTML. Elements are referenced by role, label, and position.

3

Interact

Clicks, types, scrolls, fills forms — all by element reference, not fragile CSS selectors.

4

Report

Returns a summary of what it found — errors, unexpected states, missing elements.

🌐
This is especially powerful after UI changes — instead of manually clicking through flows, ask the agent to verify them. No test scripts to write, no Selenium boilerplate.

GitHub Integration

With the GitHub MCP, you can create PRs, search issues, and manage your repo without leaving Cursor.

.cursor/mcp.json — GitHub server
{
  "mcpServers": {
    "github": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-github"],
      "env": {
        "GITHUB_PERSONAL_ACCESS_TOKEN": "${env:GITHUB_TOKEN}"
      }
    }
  }
}

Set GITHUB_TOKEN in your shell environment — never hardcode it in the file.

What This Enables

  • "Create a PR for these changes" — Agent writes a description and opens the PR
  • "What issues mention the payment flow?" — Searches issues without leaving Cursor
  • "Summarize the comments on PR #42" — Reads PR review comments
  • "Add a label to issue #15" — Direct repo management
ℹ️
Cursor has built-in git support (commits, diffs, history). For GitHub-specific features (PRs, issues, reviews), you need the MCP server.

Plugins — Share Everything as a Package

A plugin bundles rules, skills, agents, MCP configs, and hooks into a single installable package. Anyone who installs it gets your entire setup automatically.

Plugin Structure

your-cursor-plugin/ ├── .cursor-plugin/ │ └── plugin.json ← {"name": "your-plugin", "version": "1.0.0"} ├── rules/ │ ├── backend.mdc │ └── frontend.mdc ├── skills/ │ └── code-reviewer/ │ └── SKILL.md ├── agents/ │ └── post-edit-verifier.md ├── .mcp.json └── README.md

When to Create a Plugin

  • You want open-source contributors to get your project conventions automatically
  • You want to share the same setup across multiple repos in your organization
  • You want to publish to the Cursor Marketplace

Best Practices

Best Practices

Drawn from Cursor's official best practices, the prompting docs, and real-world usage across a multi-pillar project.

1. Plan Before You Code

For anything non-trivial, use Plan Mode (Shift+Tab). The agent researches your codebase, asks questions, and writes a plan. You approve before it writes code. Save plans to .cursor/plans/ — they double as team documentation.

2. Write Specific Prompts

Bad

"Add tests for auth"

Good

"Write a test for the logout endpoint in app/auth/router.py covering the edge case when the session has expired. Use the patterns in tests/unit/. Don't mock the database — use test fixtures in conftest.py."

3. Let the Agent Find Context

You don't need to @-mention every file. The agent has semantic search — it finds relevant files automatically. Only use @filename when you know the exact file. Including irrelevant files confuses the agent about what matters.

4. Know When to Start a New Chat

Start fresh when you finished a logical unit of work, the agent keeps making the same mistake, or you're switching tasks. Continue when you're debugging what it just built or iterating on the same feature. Long conversations accumulate noise.

5. Provide Verifiable Goals

Agents can't fix what they can't check. Give them tests, type checking, and linting as acceptance criteria. The best workflow: write tests first (or ask the agent to), then ask it to implement until tests pass.

6. Use Checkpoints for Safety

The agent creates checkpoints before major edits. If it goes wrong, click any checkpoint to preview and restore. This is separate from git — use git for permanent version control, checkpoints for quick undo.

7. Run Agents in Parallel

For hard problems, run the same prompt on multiple models simultaneously using worktrees — each model gets its own isolated copy. Compare results side by side and click Apply to merge the best one.

8. Use Images

Paste screenshots directly into chat: design mockups → "Implement this UI", error screenshots → "Debug this", console errors → faster than typing the stack trace.

9. Start Simple, Add Rules Gradually

Don't write 20 rules on day one. Start with one always-apply rule for core standards. Add more only when you notice the agent making the same mistake repeatedly.

How It All Works Together — A Real Session

You've seen every file. Now watch them work as a system — from the moment you open Cursor to the end of a productive session.

Step 1: You Open the Project

Step 2: You Open a File — The Right Rules Activate

You open src/templates/step_reasoner.py and type "Improve this template's prompt quality". Behind the scenes, Cursor checks every rule's globs against the open file:

⚙️
Result: core-standards.mdc (alwaysApply) + sdk-library.mdc (matches src/**/*.py) are injected. The other 4 rules are skipped. The agent knows SDK conventions without you saying anything. If you switch to app/web/src/pages/Dashboard.jsx, the SDK rule deactivates and the frontend rule activates instead.

Step 3: MCP Fetches Live Docs

You type "Update the LiteLLM integration to use the latest provider format. Use context7." The agent calls the Context7 MCP server, which fetches the current LiteLLM documentation from source. You get correct, current code on the first try — not what the model memorized from training data two years ago.

Step 4: The Agent Edits a File — Hooks Auto-Format

The agent edits src/utils/helpers.py. The afterFileEdit hook triggers, runs ruff check --fix . and ruff format ., and the file is auto-formatted. If the agent tries to run rm -rf /, the beforeShellExecution hook blocks it — the command never executes.

Step 5: You Invoke a Skill

You type /code-reviewer. The agent loads SKILL.md, follows each step (read changed files → check conventions → run lints → report issues) — the same thorough workflow every time, not a different improvised approach each session.

After the agent makes changes, the post-edit verifier spawns in its own context window. It runs tests, checks types, and runs linting in the background while you keep working. You see: "Verifier passed: 14 tests pass, types clean, no lint issues." The 200 lines of pytest output never appear in your main chat.

Step 7: Continual Learning Observes

You correct the agent during the session: "No, use ruff not flake8." The Continual Learning plugin detects the pattern across sessions and adds - Use ruff for linting, not flake8 to AGENTS.md. Next session, the agent already knows. You never make that correction again.

Part 10

Worktrees & Parallel Agents

One of Cursor's most powerful features — and the one most developers never discover. Run multiple agents simultaneously on the same codebase, each in isolation.

What Is a Worktree?

A git worktree gives you a second (or third) fully checked-out copy of the same repo in a separate folder — each on its own branch, completely independent. Cursor automates this entirely — you don't run git worktree add manually.

Best-of-N: Same Prompt, Multiple Models

1

Ensure a single Git repo

Open with File → Open Folder (not "Add folder to workspace"). The feature is hidden in multi-root workspaces.

2

Click the model selector

Look for Use Multiple Models — separate from Auto / Max Mode toggles.

3

Select models

Select 2–3 models (e.g., Composer 1.5 and Claude Sonnet).

4

Type your prompt

Both models run simultaneously — each in its own worktree, each making its own edits.

5

Click Apply

Review two cards in the chat. Click Apply on the one you prefer — Cursor merges it into your main branch.

SituationUse
You want the best possible result for a hard problemWorktree — Best-of-N
You want to compare two approaches side by sideWorktree — parallel agents
You have two completely unrelated tasksWorktree — run them in parallel
Routine edit, simple fix, quick questionSingle agent — worktrees add overhead
You're on the Pro plan watching costsSingle agent — worktrees multiply usage

worktrees.json — Setup Script

.cursor/worktrees.json — Python (uv)
{
  "setup-worktree": [
    "uv sync",
    "cp $ROOT_WORKTREE_PATH/.env .env"
  ]
}
.cursor/worktrees.json — Node.js
{
  "setup-worktree": [
    "npm ci",
    "cp $ROOT_WORKTREE_PATH/.env .env"
  ]
}

$ROOT_WORKTREE_PATH points to your main working directory so you can copy files like .env across. Note: LSP (linting/autocomplete) is not supported in worktrees — the agent can still run commands and tests, but won't get inline lint feedback.

Part 11

Model Selection & Reducing Waste

Every Cursor chat consumes tokens. The model you pick determines both quality and cost — and the default behavior is often not optimal for the full range of tasks you actually do.

Two Usage Pools

PoolWhen It's UsedPro Plan Includes
Auto + ComposerWhen you select Auto or Composer 1.5Generous included usage
API poolWhen you pick a specific model (Claude, GPT, Gemini)$20/mo

If you're burning through your $20 API pool on simple tasks, switching those to Auto or Composer 1.5 extends your budget significantly.

Which Model for Which Task

TaskBest ChoiceWhy
Understanding code, grepping, Q&AAsk mode + AutoRead-only — no premium reasoning needed
Simple edits, small refactorsAuto or Composer 1.5Fast, included in the generous pool
Multi-file refactors, architectureClaude Sonnet or PremiumWorth the quality lift
Security review, complex reasoningClaude Opus or PremiumReasoning depth matters
Subagent tasks (tests, lint, verify)model: fast in agent fileMechanical work — fast model is sufficient
Best-of-N comparison1 fast + 1 premiumMost quality gain at half the cost of 2 premium

Practical Cost Tips

  1. Use Ask mode for exploration — switch to Agent only when you're ready to make edits.
  2. Start new chats when switching tasks — long conversations accumulate context, which costs more per turn.
  3. Don't over-@mention files — every @filename is loaded into context. Let the agent search instead.
  4. Best-of-N: 2 models max — 1 fast + 1 premium gives a comparison at half the cost of 2 premium models.
  5. Turn off on-demand usage in billing settings if you want a hard spending cap. Without this, Cursor auto-charges overage at the same rates — which can accumulate to $200–300+ without notice.
  6. Subagents multiply token usage — 3 parallel subagents = ~3x tokens. Use parallel execution when time savings justify the cost, not reflexively.
Part 12

Keeping Your .cursor/ Setup Lean

As your project matures, .cursor/ accumulates skills, rules, and agents. More isn't always better — redundant skills create noise that makes selection less accurate.

Skills: Watch for Overlap

The agent decides which skill to use based on the description field alone. If two skills have similar descriptions and overlapping trigger words, the agent may invoke the wrong one.

SymptomLikely Cause
Agent keeps invoking the wrong skillTwo skills with similar trigger words
Agent uses a skill when you didn't askDescription is too broad
Agent asks which skill to useTwo skills with identical use cases

Use disable-model-invocation: true for skills that are rarely needed or take a long time — release workflows, deep research sessions, ecosystem scans.

Rules: Keep alwaysApply Minimal

Only one rule should have alwaysApply: true — your core standards. Everything else should use globs so it only loads when relevant files are open.

The Right Size for a Mature Setup

ItemReasonable CeilingWarning Sign
Rules6–8More than 10 with alwaysApply: true
Skills8–12Overlapping descriptions, wrong skill invoked
Subagents2–4Vague descriptions, agent doesn't know when to use
Plans0–3 activeMore than 5 that are done/stale
🎯
Start lean. Add only when you notice a repeated gap — the agent making the same mistake, a workflow you explain manually every time, or a task that always needs a specific model.
