Chapter One

Why Most
Prompts Fail

Prompt failures are not a wording problem. They are a structure problem. Every vague instruction is a decision you've accidentally delegated to the model.

Open any LLM. Type: "Summarize this article." You'll get a summary. Sometimes good. Often generic. Occasionally wrong. That unpredictability isn't the AI being difficult — it's the prompt being underspecified.

A prompt like "summarize this article" is simultaneously missing: a role, a goal, constraints, a format, and a reasoning strategy. The AI fills in all of those blanks itself. Every time. Randomly. That's why results vary.

The fix is not better wording. It is structure.
A structured prompt with a cheap model outperforms an unstructured prompt with an expensive model. The structure provides the scaffold. The model provides the intelligence. Neither works without the other.

This guidebook shows you the structure — backed by 14 published studies and 4 Sadhira AI experiments — that turns unpredictable AI output into reliable, production-grade results.

Chapter Two

The 9-Section
Architecture

Nine sections. A specific order. Grounded in how transformer attention is allocated across long contexts — not convention, not intuition.

Fig. 1 — The U-Shaped Attention Curve (Liu et al., 2023)

LLMs show the same U-shaped attention curve as humans in memory experiments. Information at the start and end of a prompt is recalled most reliably; information buried in the middle is recalled least reliably (Liu et al., 2023). The 9-section ordering is engineered around this curve.

Chapter Three

Section-by-Section
Guide

What to write in each section, why it matters, and the exact language patterns that produce reliable results.

Do it in the app. All nine steps can be accomplished in Sadhira AI Context Studio — a guided wizard that walks you through each section with the exact formulas from this guidebook. No coding required. Use the Context Studio in the Sadhira AI app to build prompts step by step.

① Role — Who the AI Is

Start with You are. Add seniority, domain, and a scope boundary to prevent the Persona Effect — strongly established personas expand into adjacent domains over long interactions (Shanahan et al., 2023).

Too vagueYou are an expert.
Specific + scopedYou are a senior application security engineer.
Scope: Review application-layer code only. Do not assess infrastructure or team practices.

② Goal — What Success Looks Like

The goal must be imperative, not declarative. Imperative framing creates a completion commitment; declarative framing creates awareness without obligation (Wierzbicka, 1987).

Declarative (weak)Goal: Analyze the data.
Imperative (strong)Your mission: Surface every statistically significant anomaly in Q4 revenue — accomplish this fully.

③ Rules — Non-Negotiable Behaviors

Write rules as guarantees, not preferences. Order them most-critical first — models apply earlier rules more reliably when instructions conflict (Zhang et al., 2025).

  • Every vulnerability must cite the exact file path and line number.
  • Every finding must include a working code fix, not just a description.
  • Rank findings: Critical → High → Medium → Low.
  • If the code is secure, state that explicitly.

④ Style — Persona's Voice

Separate voice and tone from output format. Mixing them — "Be formal and use bullet points and no headers" — is parsed inconsistently (Sweller, 1988). Style is how the AI speaks; format is what shape the output takes.

MixedBe formal, use bullet points, no preamble, and be direct.
SeparatedStyle: Formal, analytical, third-person. No hedging.
Output format: Return ONLY a ranked bullet list. No preamble.

⑤ Reasoning Strategy — How the AI Thinks

For multi-step or analytical tasks, specify the reasoning approach. Without it, the model may jump to conclusions. Common strategies: step_by_step (sequential), multiple_angles (consider alternatives), verify (check before concluding).

ImplicitAnalyze the data and identify anomalies.
ExplicitReason step by step: (1) Identify each metric and its baseline. (2) Compute deviation. (3) Rank by magnitude. (4) State confidence before interpretation.

⑥ Examples — Few-Shot Anchors

2–5 input→output demos in the middle zone produce more stable calibration than examples at the start (Li et al., 2025). Place them after rules so the model understands constraints before seeing demos. More than 5 rarely improves quality.

Example placement: Rules first, then examples. Each example should show the exact format you want — including structure, level of detail, and how edge cases are handled.

⑦ Output Contract — Exactly What to Return

The most underused section. Start with Return ONLY and specify the exact shape. This goes just before the task — for maximum compliance.

Output contract examples
Return ONLY a ranked bullet list of findings.
Each bullet: [metric] | [delta %] | [magnitude σ] | [confidence] | [cause]
No preamble. No summary paragraph.

---

Return ONLY valid JSON matching this schema:
{"sentiment": "positive|negative|mixed", "confidence": 0.0–1.0, "reasoning": "one sentence"}
No markdown wrapper. No explanation outside the JSON.

⑧ Guard Rails — What to Never Include

Use positive redirects, not bare negation. "Do not speculate" is weaker than "Base every claim on the data provided." Chapter 4 covers this fully — including the most common ineffective instruction on the internet.

⑨ Task — The Trigger (Always Last)

The task must always be last. Placing it in the recency zone yields +9.7 BLEU (Li et al., 2023). Anything before it is context for it.

Task at startAnalyze this data: [data below]. You are a senior analyst...
Task at end[Role, goal, rules, format, guard rails above.]

Your task: Analyze the Q4 revenue data below and surface every anomaly above 2σ.

Keep the task concise. Move detail into rules or context. For long inputs, mirror key instructions at the bottom — "Surface every anomaly above 2σ. Ranked bullet list only." — so the model sees them in the recency zone.

Chapter Seven

The 20 Most
Common Mistakes

A reference checklist. Review your prompt against this list before sending it.

  • No role at all. The AI defaults to a generic helpful assistant. Specify who it is.
  • Generic role. "You are an expert" is meaningless. Add seniority, domain, and context.
  • Task at the beginning. The task should always be last. Anything before it is context for it.
  • Declarative goal. "Goal: analyze the data" describes an area. "Your mission: identify every anomaly above 2σ — accomplish this fully" defines done.
  • Writing "Do not hallucinate." The most common ineffective instruction. Replace with: "Every claim must be supported by the source material. If not present, state: 'Not found in the provided material.'"
  • Bare negation in guard rails. "Do not speculate" fails more often than "Base every claim on the data provided."
  • Suggestive modals in hard constraints. "You should include a confidence score" is optional. "Every finding must include a confidence score" is not.
  • No output contract. Without one, the AI decides the format. It will produce more than you need — with preamble and unsolicited conclusions.
  • Format and style mixed together. "Be formal and use bullet points and no headers and be direct" is one instruction parsed inconsistently. Separate voice from structure.
  • Role without scope. Specific roles expand. "Security engineer" will review your entire infrastructure. Add a Scope: line.
  • Examples at the start. Examples should go after rules — so the model understands constraints before seeing demos.
  • Too many examples. More than 5 rarely improves quality. 2–3 representative examples outperform 8 exhaustive ones.
  • Vague "be thorough" instructions. Not measurable, not binding. "Every finding must include at least 3 supporting data points" is.
  • No instruction for missing information. If data is missing, what should the AI do? State it explicitly.
  • Passive voice in instructions. "Confidence scores should be included" is weaker than "Include a confidence score in every finding."
  • No reasoning strategy for multi-step problems. Without step_by_step, the model jumps to conclusions.
  • Conflicting instructions without priority. If two rules conflict, the model resolves it arbitrarily. State priority explicitly.
  • Not specifying the audience. "Write for a non-technical audience" is meaningfully different from "Write for a senior engineer."
  • Not using "Return ONLY". The two words that most reliably suppress preamble, hedging, and unwanted conclusions.
  • Not iterating. A first prompt is a hypothesis. Run it, identify which section failed, fix that section. Good prompts are engineered, not typed.

Layer 1 — Build: Context

Turn the 9-section architecture into a structured Python object. The SDK handles section ordering, provider-specific formatting, and imperative goal framing automatically.

Python — mycontext-ai
from mycontext import Context, Guidance, Directive, Constraints

ctx = Context(
    guidance=Guidance(
        role="Senior revenue analyst with 10 years of FP&A experience",
        goal="Surface every statistically significant anomaly in Q4 revenue",
        persona_scope="Limit analysis to the data provided. Do not forecast.",
        rules=[
            "Back every claim with a specific number from the data",
            "Flag every anomaly above 2 standard deviations from Q3",
            "Separate observations from interpretations",
            "State confidence level (high/medium/low) for every interpretation",
        ],
        style="Formal, analytical, third-person. No hedging.",
    ),
    directive=Directive("Analyze the Q4 revenue data below for anomalies."),
    constraints=Constraints(
        output_contract="Return ONLY a ranked bullet list: metric | delta % | magnitude | confidence | interpretation.",
        must_not_include=["speculation", "forecasts", "generic commentary"],
    ),
    research_flow=True,         # 9-section ordering — always correct
    provider_hint="anthropic",  # XML delimiters + positive constraint reframe
)

result = ctx.execute(provider="anthropic", model="claude-opus-4-5")

# Same context, three provider renderings — no manual reformatting
ctx_openai = ctx.model_copy(update={"provider_hint": "openai"})   # Markdown headings

Layer 2 — Optimize: PromptArchitect

Takes any raw prompt string and applies the 9-section architecture automatically — parsing what exists, scoring quality, rewriting weak or missing sections, and returning a before/after diff. Also builds complete prompts from a plain task description.

Three entry points — parse() detects sections heuristically (no LLM). build() constructs a full 9-section prompt from a task description (1 LLM call). improve() rewrites an existing prompt and scores the change.
Python — PromptArchitect
from mycontext.intelligence import PromptArchitect

arch = PromptArchitect(provider="openai", model="gpt-4o-mini")

# ── Improve an existing weak prompt ──────────────────────────────
result = arch.improve("You are an analyst. Summarize this data.")

print(result.summary())
# Score: 18% → 74%  (+56%)
# Added sections: role, goal, rules, style, reasoning, output_contract, guard_rails
# Resolved 5 issues: missing_goal; missing_rules; generic_role; ...

print(result.diff_report())
# [STRENGTHENED]  § ROLE
#   BEFORE: analyst
#   AFTER:  Senior data analyst specializing in business metrics and trend analysis
#   WHY:    Existing content was weak — upgraded per: Include seniority level

# [ADDED]  § GOAL
#   AFTER:  Identify the three most significant patterns and state their business impact
#   WHY:    Section was absent; added: Use imperative framing

# ── Build from a task description ────────────────────────────────
result = arch.build("Analyze customer churn and identify at-risk segments")
print(result.improved_prompt)   # Complete 9-section prompt, ready to use

Layer 2 — Optimize SDK Templates: GuidanceOptimizer

For SDK templates that use Guidance objects — audits every rule for the three most common weaknesses and rewrites only the weak ones using an LLM. Binding rules are kept exactly as written.

Three weaknesses it targets: (1) Suggestive modals — "should/try to/ideally" → "must/always/never". (2) Vague directives — "be accurate" → a specific, testable criterion. (3) Under-specified rules — anything under 5 words with no measurable condition.
Python — GuidanceOptimizer
from mycontext.intelligence import GuidanceOptimizer
from mycontext.foundation import Guidance

guidance = Guidance(
    role="Data analyst",
    rules=[
        "Try to look for patterns",          # weak: suggestive modal
        "You should mention limitations",    # weak: suggestive modal
        "Be accurate",                       # weak: vague directive
        "Every claim must cite the specific data point that supports it",  # binding — kept
    ],
)

opt = GuidanceOptimizer(provider="openai", model="gpt-4o-mini")

# Audit only — no LLM call
audit = opt.audit(guidance)
print(audit.summary())
# Rules: 4 total  |  1 binding  |  3 weak  |  Strength: 28%

# Optimize — rewrites weak rules only
result = opt.optimize(guidance)
print(result.audit_report())
# Rule strength: 28% → 91%  (+63%)  |  3/4 rules rewritten

print(result.optimized_guidance.rules)

#   "Identify and quantify every pattern — report the metric and its value.",

Layer 3 — Evaluate: QualityMetrics + OutputEvaluator

Two built-in evaluators — no external dependencies, no LLM cost in heuristic mode. One scores your prompt before you send it. The other scores the model's response after you receive it. Together they close the full feedback loop.

QualityMetrics — scores the prompt itself across 6 dimensions: Clarity, Completeness, Specificity, Relevance, Structure, Efficiency. Runs in <1ms heuristically. Use it as a gate before sending — catch missing roles, vague rules, and weak directives before they cost you a model call.
Python — QualityMetrics (prompt quality, before sending)
from mycontext.intelligence import QualityMetrics

qm = QualityMetrics()   # heuristic by default — free, instant

score = qm.evaluate(ctx)
print(f"Overall: {score.overall:.0%}")   # e.g. 72%

# Per-dimension breakdown
for dim, s in score.dimensions.items():
    print(f"  {dim.value}: {s:.0%}")
# clarity:       85%   ← strong binding language, low pronoun ratio
# completeness:  60%   ← missing examples
# specificity:   70%   ← good, could add edge cases
# relevance:     80%
# structure:     75%
# efficiency:    65%

# Issues the evaluator caught
for issue in score.issues:
    print(f"  ! {issue}")
# ! No examples -- add concrete examples of expected input/output
# ! Directive is long (112 words) -- move detail into rules/constraints

# Actionable suggestions
for s in score.suggestions:
    print(f"  → {s}")
# → Add concrete examples and tighter constraints to reach excellence.
OutputEvaluator — scores the model's response across 5 dimensions: Instruction Following, Reasoning Depth, Actionability, Structure Compliance, Cognitive Scaffolding. Heuristic by default; switch to LLM mode for deeper analysis. Detects hedging, vague conclusions, missing structure, and refusals.
Python — OutputEvaluator (output quality, after receiving)
from mycontext.intelligence import OutputEvaluator

evaluator = OutputEvaluator()         # heuristic — free, instant

# evaluator = OutputEvaluator(mode="hybrid")   # heuristic first, LLM only if borderline

score = evaluator.evaluate(context=ctx, output=llm_response)
print(f"Overall: {score.overall:.0%}")   # e.g. 81%

# Per-dimension breakdown

Using both together — the quality gate pattern

Python — full quality gate
from mycontext.intelligence import QualityMetrics, OutputEvaluator

qm = QualityMetrics()
evaluator = OutputEvaluator()

# ── Step 1: Gate the prompt before sending ────────────────────────
prompt_score = qm.evaluate(ctx)
if prompt_score.overall < 0.65:
    print("Prompt quality too low — fix before sending:")
    for issue in prompt_score.issues:
        print(f"  ! {issue}")
else:
    # ── Step 2: Send and score the output ─────────────────────────
    result = ctx.execute(provider="openai", model="gpt-4o-mini")
    output_score = evaluator.evaluate(context=ctx, output=result.response)

    print(f"Prompt quality:  {prompt_score.overall:.0%}")
    print(f"Output quality:  {output_score.overall:.0%}")

    if output_score.overall < 0.60:
        print("Output quality low — check these weaknesses:")
        for w in output_score.weaknesses:
            print(f"  - {w}")

Optional deeper layer: eval_criteria

When heuristic scoring isn't enough — for experiment validation, benchmarking new templates, or catching nuanced failures the regex can't see — eval_criteria provides pre-built LLM-judge rubrics that plug directly into DeepEval. Use on-demand, not on every run.

When to use: The built-in heuristic evaluators catch structural problems fast and free. eval_criteria catches semantic problems — a claim that looks evidenced but isn't, a data gap that's hedged over instead of named, causation asserted without a mechanism. Run it when you need ground truth on a set of test cases, not in your production loop.
Python — eval_criteria (optional, requires: pip install deepeval)
